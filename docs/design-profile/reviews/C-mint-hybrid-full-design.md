## 7. 재생성 스크립트와 실행 환경
- 위치: `docs/design-profile/figma-scripts/`. 실행 방법은 같은 폴더의 `README.md`에 있습니다.
- 환경
  - Figma 개인 계정, Starter 플랜, Full 좌석, MCP 서버 `figma-personal`
  - 글꼴: Noto Sans KR(Pretendard 없음)
  - 문법 검사: Node 20.19.5
- 재현성 주의
  - MCP는 코드를 **본문 문자열로만** 받고 파일 경로를 받지 않습니다. 실행 에이전트가 2만 자 넘는 코드를 옮겨 적다가 숫자 표기 두 곳을 다르게 보낸 적이 있습니다(첫 실행, 값은 같음). 그 뒤 실행에서는 공통 블록을 `diff`로 대조하게 했습니다.
  - 노드 ID는 파일마다 다릅니다. 스크립트는 이름으로 찾기 때문에 같은 파일에서는 다시 실행해도 안전합니다.

## 10. 남은 작업(한도가 풀린 뒤 순서)
1. `s2` → `s6` 실행(5회). 실패하면 그 파일만 고쳐 다시 실행합니다.
2. 그룹 섹션별 스크린샷(8회 이하) → 저장소 `screens/C/`에 저장합니다.
3. 시각 결함 수정(필요한 만큼) → 수정 후 스크린샷 1회
4. 검증 표 갱신: 생성 수, 노드 ID, 결함
- 필요 호출: 약 14–16회. 월 한도가 다시 차기 전에는 **Professional 플랜이나 다음 달 한도**가 필요합니다.

## 11. 엔진 관점 발견
1. **Figma-first는 호출 예산이 1순위 제약입니다.** 29개 화면 + 컴포넌트에 최소 12회가 들고, 확인 스크린샷까지 넣으면 Starter 한 달 한도를 넘습니다. Design Direction의 필수 입력에 "MCP 플랜과 남은 호출 수"를 넣고, 화면 수 × 호출 수를 미리 계산해야 합니다.
2. **로컬에서 완성한 뒤 실행하는 방식은 유효했습니다.** 7회 중 스크립트 오류는 1회(GROUP 제약)뿐이었습니다. 엔진에 "스크립트 문법 검사 + 멱등 + 이름 기반 찾기"를 Figma-first 실행 규약으로 둘 만합니다.
3. **변형의 글자 기본값은 세트 전체에 하나입니다.** 변형마다 다른 기본 문구를 두려면 글자 속성을 따로 두어야 합니다. 이번에는 검색칸 기본 문구가 "입력"으로 보인 결함으로 드러났습니다. 컴포넌트 설계 규칙 후보입니다.
4. **모드 1개 제약 때문에 승인 토큰에 묶인 기존 컴포넌트를 테마에 재사용할 수 없었습니다.** 테마 전환을 고려하면 컴포넌트는 처음부터 의미 변수(테마 컬렉션)에 묶어야 합니다. `theme-separation.md`의 2층 구조를 뒷받침합니다.
5. 명세 문구 공백 3건과 모호한 배치 10건이 드러났습니다. Visual Review 전에 "문구 없음" 목록을 UX Spec 개정 후보로 모으는 단계가 필요합니다.
