# 제안: 프로젝트 테마를 UX Specification 재승인과 분리

- 상태: **제안서**(엔진·승인 문서·토큰 미수정). 2026-11-10.
- 배경: SMAPSH 브랜드 방향은 초록 계열인데, 승인된 UX Specification r1의 `04-ui-system.md`는 주 행동 색을 파랑(`color.action.primary = #1D5BD0`)으로 정의합니다. 현재 엔진 규칙(`reference/preview.md`: "토큰 변경은 UX 설계 변경")으로는 색 하나를 바꿔도 UX Spec을 `reopen`·재승인해야 합니다.
- 전제: 테마는 **개발자가 프로젝트 설정 파일로 바꿉니다.** 관리자용 테마 UI는 두지 않습니다.

## 1. 원칙: 무엇이 UX 결정이고 무엇이 테마인가

| 층 | 예 | 바뀌면 | 승인 |
|---|---|---|---|
| 의미 토큰(이름과 용도) | `color.action.primary` = "주 버튼 배경, 링크, 선택 상태" | 화면의 의미가 바뀜 | UX Spec(04) |
| 의미 토큰의 **제약** | 본문 대비 ≥ 4.5:1, `action.onPrimary` on `action.primary` ≥ 4.5:1, 상태 색은 브랜드 색과 구분 | 접근성·정보 구분이 바뀜 | UX Spec(04) |
| 브랜드 원시 토큰(값) | `brand.primary.600 = #……` | 화면의 색만 바뀜 | **테마 설정**(제약 자동 검증 + 개발자 확인) |
| 의미 → 원시 연결 | `color.action.primary → {brand.primary.600}` | 어떤 원시 색을 쓰는지 | 테마 설정(제약 검증 통과 시) |

UX Spec이 승인하는 것은 **의미와 제약**이고, 테마는 **제약을 지키는 값**만 고릅니다.

## 2. 파일 구조(SMAPSH 예)

```
docs/design/04-ui-system.md            # 승인 문서: 의미 토큰 + 제약(대비 쌍, 상태 구분 규칙)
docs/design-profile/tokens.json        # DTCG: 의미 토큰. 값 대신 {brand.*} 별칭
docs/design-profile/theme.json         # DTCG: 브랜드 원시 토큰(개발자 설정) — 테마 하나 = 파일 하나
docs/design-profile/theme-check.md     # 테마 검증 결과(대비, 상태 구분)와 확인 기록
```

## 3. 대비·상태 색 검증

테마를 바꿀 때 자동으로 검사할 항목(04 1.2의 '대비' 열을 기계가 읽을 수 있는 제약으로 옮김):

| 검사 | 기준 | SMAPSH에서 주의할 점(초록 전환 시) |
|---|---|---|
| 글자 대비 | 본문 쌍 ≥ 4.5:1, 큰 글자·경계 ≥ 3:1(04 1.2) | `action.onPrimary`(흰색) on 초록 주 색 4.5:1 이상인 진한 초록 필요 |
| 상태 색 구분 | 브랜드 주 색과 `status.success`가 서로 구분(색상 차 또는 명도 차 기준 + 글자·아이콘 병행) | 현재 성공 색 `#1B6E35`·코트 바닥 `#2F7D4F`가 초록 → 의미가 섞일 위험. 성공은 아이콘·글자 병행이 이미 원칙(04 3장)이지만, 수치 기준을 제약으로 둠 |
| 팀 색 | 청팀·백팀 색이 브랜드 색과 구분 | 청팀 파랑은 초록과 구분됨 |
| 포커스 링 | 배경 대비 ≥ 3:1 | 포커스 링을 브랜드 색에 묶으면 함께 검증 |

검증은 기존 `04` 작성 때 쓴 대비 계산과 같은 공식(WCAG 상대 휘도)을 씁니다.

## 4. 승인 문서와 충돌하지 않는 전환 절차

1. **1회 구조 전환(UX Spec 개정 1번 필요)**: 04를 "의미 토큰 + 제약" 구조로 바꾸고, 현재 값(파랑 포함)을 `theme.json`의 기본 테마로 옮깁니다. 값이 그대로라 화면은 바뀌지 않습니다. 이 개정은 UX Spec r2로 `reopen` → 수정 → 재승인.
2. **초록 테마 적용(이후 UX Spec 재승인 불필요)**: 개발자가 `theme.json`에 초록 원시 토큰을 넣고 연결을 바꿉니다 → 자동 검증(§3) → 통과하면 테마 확인 기록 → `visual_review`·`preview`만 무효화되어 다시 확인.
3. 검증에 실패하면(예: 상태 색과 구분 안 됨) 테마를 고치거나, 제약 자체를 바꿔야 하면 UX Spec 개정으로 넘깁니다.

지금은 1단계도 실행하지 않았습니다(승인 문서 수정 금지). 초록 전환을 원하면 1단계와 2단계를 순서대로 승인받아 진행합니다.

## 5. 현재 엔진에서 가능한 것과 개정이 필요한 것

| 항목 | 현재 엔진에서 | 엔진 개정 필요 |
|---|---|---|
| 04를 의미 토큰 + 제약 구조로 개정 | **가능**: `reopen --stage ux_spec` → 수정 → 재승인(기존 절차) | - |
| `theme.json` 파일 두기 | **가능**: `docs/design-profile/`는 엔진 관리 밖(경고 없음) | 엔진이 테마 파일을 인식하려면 개정 |
| 테마 변경 시 UX Spec 재승인 생략 | 불가: `preview.md`의 "토큰 변경 = UX 설계 변경" 규칙과, `design-preview/src/tokens.css` 변경이 Preview 트리 해시를 바꾸는 구조 | 규칙 개정: 테마 값 변경을 별도 분류(P0 영향 분류)로 |
| 테마 변경 시 Preview 재승인 | **현재도 발생**: 트리 해시가 바뀌면 `approved_modified`로 막힘 → `reopen --stage preview` | 테마 전용 무효화(visual_review·preview만) 자동화 |
| 대비 자동 검증 | 수작업(스크립트로 계산 가능) | 엔진 명령(예: `theme-check`)으로 |
| 테마 확인 기록(해시) | 없음 | `design.json`에 `theme` 항목(파일 해시, 검증 결과, 확인 시각) |

## 6. 범용 엔진에 둘 것과 프로젝트에 둘 것

- 엔진: 의미·원시 2층 규칙, 제약 형식, 테마 검증 명령, 테마 변경의 영향 범위(visual_review·preview만), 테마 파일 위치 설정 키.
- 프로젝트(SMAPSH): 실제 테마 값(초록), 브랜드 원시 팔레트, 상태 색 재설계 결정, 글꼴.
