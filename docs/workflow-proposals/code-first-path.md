## 3. Code-first 대체 경로 설계

### 3.1 흐름
```
ux_planning → ux_spec(승인) → design_direction(승인)
                                  │  출력: VD · 테마 · 밀도 정책 · 화면 IR(렌더러 중립)
                         ┌────────┴─────────┐
                 Figma-first 렌더러       Code-first 렌더러
              (use_figma 스크립트 생성)   (React 컴포넌트 + 목업 생성)
                         └────────┬─────────┘
                           render ledger(화면·상태별 렌더 출처·해시)
                                  │
                          visual_review(공통) → preview 승인(design-preview/ 트리 해시)
```

### 3.2 핵심: 렌더러 중립 화면 IR
- 이번 실험에서는 Figma 스크립트가 원본이고 IR(dry-run JSON)을 거꾸로 뽑았습니다. 엔진에서는 **IR을 Design Direction의 출력(원본)**으로 두고, Figma 스크립트와 React 코드를 IR에서 만드는 쪽이 맞습니다.
- IR 항목: 화면·상태 ID, 플랫폼, 노드 트리(컴포넌트 이름·변형·글자 속성), 토큰 이름(값 아님), 샘플 데이터 참조, 밀도 정책 값
- IR은 저장소 파일이라 해시를 남길 수 있습니다. 렌더러가 바뀌어도 IR 해시는 그대로입니다.

### 3.3 입력 공유와 승인 게이트 보호
| 원칙 | 내용 |
|---|---|
| 같은 입력 | 두 렌더러 모두 승인된 01–05(해시), Design Direction(VD·테마·밀도·IR), 샘플 데이터 규칙을 씁니다 |
| 읽기 전용 | 렌더러는 00–05, `state.yaml`의 승인 상태, `tokens.json`을 쓰지 않습니다. 테마는 테마 파일, 실험 변경은 IR의 `experimental` 표시 |
| 승인 위치 불변 | 최종 시각 승인은 지금처럼 `design-preview/` 트리 해시 + 06입니다. Figma는 검토 대상일 뿐입니다 |
| 실험 분리 | 승인 문서와 충돌하는 변경(배너 제거 등)은 IR 노드에 `experimental: "C안"` 표시. Visual Review가 목록으로 내고, 승인 Preview에는 들어갈 수 없습니다(UX Spec 개정 필요) |

### 3.4 Figma 중단 시 안전한 전환
1. **render ledger**(`design-render.json`, 가칭): 화면·상태마다 `{renderer, status: done|pending|failed, figmaNode?, previewPath?, irHash, at}`를 기록합니다.
2. **중단 판정**: 한도 오류, 남은 예산 0, 연속 실패 2회 중 하나면 Figma 경로를 `paused`로 표시하고 남은 화면은 `pending`으로 둡니다. 이미 만든 노드는 지우지 않습니다.
3. **전환**: 사용자가 `--renderer code`를 승인하면 `pending`인 화면만 Code-first로 렌더링합니다. 화면마다 출처가 달라도 됩니다(혼합 상태 허용).
4. **복귀**: 한도가 회복되면 같은 IR로 Figma 스크립트를 다시 만들고 실행합니다. 멱등이라 이미 있는 프레임은 건너뜁니다.
5. 전환은 승인 상태를 바꾸지 않습니다. `design_direction`이 다시 승인될 때만 하위 렌더가 무효화됩니다.

### 3.5 공통 Visual Review
- 입력: 렌더 결과(Figma 스크린샷 또는 브라우저 스크린샷) + IR + 밀도 정책 + 규칙 목록. 판정 형식은 `SCR-211-mobile-ux-review.md`와 같습니다.
- **Code-first의 장점**: 실제 렌더링이라 크기·넘침·가림을 계산이 아니라 **측정**할 수 있습니다(DOM 박스). 360·390·430 폭에서 측정합니다.
- 자동 점검: 대비(계산된 스타일), 터치 크기(박스 ≥ 44), 고정 요소 가림(행 박스 × 고정 박스 교차, 스크롤 위치별), 첫 화면 행 수, 안전 영역 여백, 토큰 외 값(인라인 hex·px), 실험 표시 노드 목록

### 3.6 재현성과 검증 가능성
| 항목 | Figma-first(이번) | Code-first(제안) |
|---|---|---|
| 생성물 | Figma 노드(파일 밖, ID가 파일마다 다름) | 저장소 파일(코드·목업) |
| 전달 | MCP에 코드 문자열을 그대로 붙여 보냄(옮겨 적다 틀린 적 있음) | 파일을 직접 씀 |
| 실행 검증 | 모의 실행(dry-run) + 실제 호출 | 타입 검사, 단위 테스트, 빌드 |
| 고정 | 버전 ID를 읽지 못함 | 트리 해시(기존 엔진) |
| 비용 | 호출 한도(월 단위) | 로컬 실행(한도 없음) |

## 4. 최소 PoC 계획(SCR-211 명단 1개 화면)

### 4.1 범위
- 대상: **SCR-211 ST1 기본(mobile)**. 여유가 있으면 ST3(빈 상태)를 상태 전환만으로 추가합니다.
- 위치: **`experiments/c-preview-poc/`(가칭)**. 엔진이 관리하는 `design-preview/`가 아니므로 정식 Preview를 시작하지 않고, 승인 해시에도 영향이 없습니다.
- 입력: `preview-handoff/C-screens.dryrun.json`의 `SCR-211 명단 / ST1 기본(C안) / mobile` 트리, `tokens.json` + C 테마 덮어쓰기(§1.2), 샘플 14명
- 출력: 3개 폭의 스크린샷, 측정 JSON, 검토표(`SCR-211-mobile-ux-review.md` 형식), IR ↔ DOM 대응표

### 4.2 기술 스택과 shadcn/ui 사용 가능성
| 항목 | 판단 |
|---|---|
| 현재 `frontend/` | Tailwind·shadcn·Radix·Lucide가 **없음**(React 19, Vite 7만 있음). PoC에서 새로 설치해야 함 → **의존성 설치 승인 필요** |
| shadcn 부품 | SCR-211에 필요한 것은 Button, Input, Toggle(FilterChip), Switch, Badge 5개(`component-mapping.md`). PersonRow, PageHeader, AppNav는 직접 만듦 |
| 설치 방식 | `shadcn` CLI는 레지스트리에서 코드를 내려받아 파일로 복사합니다(네트워크 + 외부 코드). 받은 코드는 검토한 뒤 써야 합니다. 대안은 부품 코드를 손으로 옮겨 적는 것(Radix 패키지만 설치) |
| 테마 | CSS 변수 2층: `tokens.css`(04 값) + `theme-c.css`(§1.2 덮어쓰기). 개발자 설정으로 테마 파일만 바꾸면 되는 구조를 검증합니다 |
| 글꼴 | Pretendard(VD-001)를 실제로 써서, Figma의 Noto Sans KR 대체와 차이를 봅니다(웹 글꼴 로딩 VD-003은 미결정 → 로컬 파일 또는 CDN 중 결정 필요) |

### 4.3 검증 기준(모바일 3개 폭)
| 항목 | 360×800 | 390×844 | 430×932 | 근거 |
|---|---|---|---|---|
| 첫 화면 행 수(측정) | ≥ 7.9 | ≥ 9.4 | ≥ 10.9 | C안 계산값(헤더 56 + 검색 띠 56 + 컨트롤 104, 탭 98, 360은 칩 두 줄 +40), B안 실측 9.46 |
| 행 높이 / 간격 | 56 / 0 | 같음 | 같음 | 밀도 유지 |
| 하단 탭 | 64 + 안전 영역, 현재 탭 표시(옅은 청록 + 굵은 글자) | 같음 | 같음 | B안 구조 |
| 목록 아래 여백 | ≥ 탭 높이 + 안전 영역 + 16 | 같음 | 같음 | 가림 방지 |
| 고정 요소 가림 | 없음('게스트 추가'가 상단이라 떠 있는 버튼 없음) | 같음 | 같음 | B안 결함 해소 확인 |
| 터치 크기 | 모든 누름 대상 ≥ 44(헤더 버튼은 보이는 높이 36 + 누름 영역 44) | 같음 | 같음 | 04 |
| 대비 | §1.2 쌍 전부 | 같음 | 같음 | WCAG |
| 토큰 외 값 | 0(실험 값 X6·X10은 목록으로) | 같음 | 같음 | - |
- 측정 도구: 브라우저 스크린샷과 DOM 측정에는 Playwright 같은 도구가 필요합니다. 이것도 의존성 설치라 **승인이 필요**합니다. 승인되지 않으면 브라우저 개발자 도구로 직접 측정하고 '수동 측정'으로 표시합니다.

### 4.4 실험용으로만 분리할 변경
배너 제거, '게스트 추가' 상단, Teal Mint 테마, 탭 64, 헤더 버튼 36, 칩 반경 16. 코드에서는 `data-experimental="C안"` 속성으로 표시하고, 검토표에 승인 명세와의 차이로 나열합니다.

### 4.5 단계와 승인 지점
1. 실험 폴더 생성과 의존성 목록 확정 → **승인**(설치 여부, shadcn CLI 사용 여부, Pretendard 로딩 방식)
2. `tokens.css` + `theme-c.css` 생성(`tokens.json`에서 스크립트로 만들고, 손으로 입력하지 않음)
3. IR → JSX 변환(SCR-211 한 화면, 사람이 확인)
4. 3개 폭 측정·스크린샷 → 검토표
5. Figma B안(`13:256`) 스크린샷, IR과 비교 → 보고
- 예상 산출 파일: 실험 폴더 1개, 검토표 1개, 스크린샷 3장. 승인 문서와 `state.yaml`은 바뀌지 않습니다.
